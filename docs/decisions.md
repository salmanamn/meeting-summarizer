# Decisions

## D1 — Shape: a recording in, a summary out
- A meeting recording (and, from M3, optional PDF or DOCX attachments) is uploaded to Blob storage. A Python Function triggered by the new blob transcribes it, asks an LLM for a summary in a fixed JSON shape (decisions, action items with owners, open questions), and stores the result in Cosmos DB. One recording is one job.
- M1 runs the same steps in one process on the laptop (`scripts/summarize_file.py`) to prove the models and measure them; the Function, the trigger and the stores come in M2.
- Same rule as the earlier projects: the code that runs on the laptop runs in the Functions host and on Azure; only configuration differs (D8).

## D2 — Transcription on the laptop: faster-whisper, Whisper small, English
- faster-whisper 1.2.1 on CTranslate2 4.9, CPU, int8, Whisper small (`stt-small`): the model and the PyAV pin (`av<19`) measured and chosen in Project 4. Meetings are English to start (`STT_LANGUAGE=en`; empty lets Whisper detect the language from the first 30 seconds).
- Long-form audio: how Whisper goes through a whole recording is D13. Either way the voice-activity filter removes silence first, and no piece is conditioned on the previous text, so one misheard piece cannot repeat through the rest.
- Timestamps are kept per segment: the summary cites them as evidence (D4).
- The attendees' names go to Whisper as hotwords on every window. Without them, Whisper small wrote "Lina" in the first minute and "Lena" later in the same recording; the owner of an action item is only as good as the spelling of the name (D6).

## D3 — Transcription on Azure: Speech batch transcription, REST API 2025-10-15
- **Status:** built in M6 against the documented API (D44–D47), fake-tested only; first run on Azure in M7
- Batch transcription is the Speech API made for recordings in storage: an asynchronous job (submit, then poll or receive a web hook), with diarization. The current GA version of the speech to text REST API is `2025-10-15` (`/speechtotext/transcriptions:submit?api-version=2025-10-15`); `v3.0` and the `3.2` previews were retired on 2026-03-31, so nothing older is used.
- Region (Speech regions table, speech to text tab): `uaenorth` has real-time and batch transcription, and neither fast transcription nor Whisper via batch transcription. Fast transcription (synchronous, under 2 hours) would be simpler but is not in the lab's region; batch it is.
- Audio access without keys or SAS: the Speech resource's **system-assigned** identity (a user-assigned one is not supported for this) gets Storage Blob Data Reader on the recordings account, the account allows that Speech resource as a resource instance (trusted Azure services), and the job gets a plain blob URL. `destinationContainerUrl` is not used: it needs a SAS and an account open to all networks; results are read from the job's result files instead.
- The Function talks to a `Transcriber` interface (`src/meeting/stt.py`), so the Azure transcriber replaces faster-whisper by configuration. Whisper inside the Function on Azure stays possible and is measured against batch transcription in M7.

## D4 — The summary contract: strict schema, limits afterwards, grounded in the transcript
- `src/meeting/summary.py`: `MeetingSummary` = `title`, `overview`, `decisions[]` (`text`, `evidence`), `action_items[]` (`task`, `owner`, `due`, `evidence`), `open_questions[]` (`question`, `evidence`).
- `SUMMARY_JSON_SCHEMA` is sent as `response_format: json_schema` with `strict: true`, inside Azure OpenAI's strict subset: every object lists all properties as required and sets `additionalProperties: false`; optional values are `["string", "null"]`; no length keywords. Lengths and counts are enforced afterwards by Pydantic (`extra="forbid"`). Unit tests keep the schema and the models naming the same fields.
- Grounding after validation (`ground()`): an evidence timestamp must fall inside a transcript segment, and an owner must be named in the transcript or be an attendee; otherwise the field becomes null and a warning says why. Items are kept, only the unsupported field goes. Empty lists are a valid answer, and a meeting where nothing was decided must produce none (D7).
- The transcript is untrusted input (anyone in a meeting can say "ignore your instructions"): it goes inside a `<transcript>` block that its own text cannot close, and the system prompt says it is data. Errors about an invalid answer name the field and the problem, never the content.
- Transcripts longer than `TRANSCRIPT_MAX_CHARS` (40,000 characters, roughly an hour of speech) are refused before any model call; splitting long meetings is M3's work. An answer cut off by the token limit is reported as such.

## D5 — The model: one OpenAI-compatible client
- One `openai` SDK client (as in Projects 3 and 4): Ollama's `/v1` locally, the Azure OpenAI v1 endpoint with Entra ID on Azure. `CHAT_REASONING_EFFORT` switches the request to the reasoning-model shape (`reasoning_effort` + `max_completion_tokens`, no `temperature`); empty locally.
- Local model to start: `phi4-mini:3.8b` on Ollama 0.40.15 (MIT, no thinking mode, already on disk from Projects 3 and 4), temperature 0, at most 1,500 output tokens, 16k context. Azure: gpt-5.4-mini (Project 3 D19). Comparing models on real meetings is M3.

## D6 — Owners come from what was said, not from who spoke
- Whisper does not tell speakers apart, and Azure's diarization labels speakers `Guest-1`, `Guest-2`, not by name. A name only reaches the summary when someone says it ("Omar, please send…") or when it is on the attendee list. So the owner of an action item is the name the meeting gives it; "I will update the release notes" has an owner only if the speaker can be identified from the text.
- Speaker labels, when a transcriber provides them, are shown in the transcript (`[00:12] Guest-1: …`); they are never turned into names.

## D7 — Test meetings are synthetic, scripted, and carry their answers
- `eval/meetings/<ID>.json` holds a script (speaker, line) and what a correct summary contains (`expect`: number of decisions and open questions, each action item's owner and task keywords). `scripts/make_meeting.py` speaks it with Piper, one voice per participant from the multi-speaker `en_US-libritts_r-medium` model (904 speakers; dataset licence CC BY 4.0), a 0.7 s pause between turns, fixed seed.
- M01: a planning meeting with 2 decisions, 3 action items, 2 open questions. M02: a status check where nothing is decided or assigned, which catches a model that invents items.
- What this measures: the pipeline end to end, and whether the summary finds what is certainly there. Not recognition of real speakers (clean synthetic audio, no overlap or noise) and not summary quality in general: real recordings and a scored evaluation come in M3.
- The M1 check (`src/meeting/expect.py`): transcript WER ≤ 15 % against the script; counts within one of the script, but zero must be exactly zero; every scripted action item found with its owner and a keyword; at most one action item more than the script.

## D8 — Configuration from environment variables; the local lab
- `src/meeting/settings.py` reads everything from the environment; the defaults are the laptop values.
- `docker-compose.yml` (project `meeting-lab`): Azurite 3.37.0 and the Cosmos DB vNext emulator (the digest pinned in Project 3) always; Ollama with `--profile ai`. Ports bound to 127.0.0.1 and the same as the ticket-triage lab's, so the two labs never run together. Emulator well-known keys only in local files that are gitignored or that say they are the emulator's.

## D9 — Model files are pinned by a lock, reused from Project 4
- `src/meeting/modelstore.py`, `src/meeting/download.py` and `scripts/fetch_models.py` come from Project 4 (its D4 and D33: lock with revision and SHA-256 per file, resumable downloads). The lock entries for `stt-small` and `stt-tiny` are copied from Project 4's lock, so the files already on disk there are the same bytes here.
- New entry: `tts-en-libritts`, for the test meetings only.

## D10 — One dependency group per job
- `pyproject.toml`: the package itself needs only `pydantic` and `openai`; `stt` (faster-whisper, PyAV), `storage` (Blob, Cosmos), `fixtures` (Piper), `models` (hub client), `dev`. The Function app (M2) ships the package with `stt` and `storage`. Piper is GPL and only makes test meetings on the laptop, so it never ships.

## D11 — A decisions index from day one
- `docs/decisions-index.md` is generated from the headings of this file by `scripts/decisions_index.py` (Project 4's script, D58 there), and `tests/unit/test_decisions.py` fails when the index is stale or a number is missing or repeated. A decision's status lives in the decision (`- **Status:** …`); updates are new decisions whose heading says `(updates Dx)`.

## D12 — Hosting on Azure: Flex Consumption, so the Blob trigger is the Event Grid one
- Flex Consumption is the serverless plan for Python 3.13 (Linux Consumption gets no Python above 3.12 and is retiring; Project 3 D1), and it supports only the event-based Blob trigger: `@app.blob_trigger(..., source="EventGrid")` with an Event Grid subscription on the storage account that calls the Functions blob extension's webhook. The polling trigger (`LogsAndContainerScan`) is not available there.
- Locally there is no Event Grid. To keep the same trigger code in both places, M2 adds a small stub (as in Project 3) that watches Azurite and posts `BlobCreated` events to the local webhook.
- Open for M2: a long recording on the Function (Flex has a 30-second host start limit and a configurable function timeout), where faster-whisper's model files live on Azure, and whether the job is split into stages (transcribe, then summarise) so a retry does not redo the transcription.

## D13 — Long recordings: pieces cut at pauses, word times, sentences as segments
- faster-whisper has two ways through a recording. `sequential` is Whisper's own: a 30-second window that slides on by the timestamps the model writes. `batched` (`BatchedInferencePipeline`) cuts the recording at pauses into pieces of at most 30 seconds and transcribes each on its own.
- Measured on M01 (`scripts/stt_modes.py`, the same script spoken with Piper seeds 0–4): on the laptop (`docs/evidence/m1-stt-modes.md`, i7-9750H, 8 threads) `sequential` went above 15 % WER in 1 of 5 runs (24.9 %) and took 48–119 s per run against 27–37 s for `batched`; in the sandbox run that set this decision (2 vCPU) it was 3 of 5 (20–45 %). Each time it skipped ahead: whole lines, including a decision and an action item, were missing from the transcript. A transcript that drops lines silently is the worst failure for a summarizer, because the summary looks complete.
- `batched` with segment timestamps (timestamp tokens inside each piece) skipped once in 5 (13 %; measured while choosing, not kept as evidence). `batched` as plain text, with times from word alignment afterwards, stayed at 3–5 % in all 5 runs and was faster than `sequential`: that is the default (`STT_MODE=batched`). Word alignment uses the model's cross-attention after decoding, so it cannot change the words; it needs `alignment_heads` in the model's `config.json` (the Systran conversion has them; the transcriber refuses a model without).
- The timed words are regrouped into sentences (at `.`, `?`, `!`): those are the segments, and the evidence times the summary cites. `sequential` stays selectable for comparison.

## D14 — Evidence is an enum of the transcript's times; an unnamed owner stays empty (updates D4, D7)
- First real run (M01 on `phi4-mini:3.8b`, 2026-11-21, `docs/evidence/m1-M01.md`): all 7 evidence fields held quotes from the transcript instead of `mm:ss` times, one of them 130 words long. Grounding removed every one (D4 worked), so the summary kept no evidence at all, and the quotes cost output tokens (622 completion tokens, 174 s on 8 threads).
- The schema is now built per transcript (`summary_schema(stamps)`): `evidence` is `anyOf` [a string `enum` of the transcript's segment times, `null`]. Locally Ollama turns the schema into a grammar, so any other value cannot be generated; Azure strict mode supports `enum` and `anyOf` the same way (`pattern` it does not). `ground()` still checks the result. The enum grows with the transcript; Azure's limits on enum size meet the long-meeting work in M3, where transcripts are split anyway.
- The same run gave "I will update the release notes" the owner `Unknown`, which grounding removed (D4 again). That line names nobody, and the summary cannot know who spoke (D6), so the script's answer for it is now `owner: null`: the check requires the item and requires it to have no owner. A guessed name would fail it, even the right one, because nothing in the words supports it.
- Not changed: the prompt. One run is not an evaluation (D7); prompt work comes with M3's.

## D15 — The upload contract: the manifest goes last and is the only blob that triggers (updates D12)
- A meeting is a folder `incoming/<meeting-id>/`: the recording, up to 5 attachments (PDF, DOCX; read from M3), and `meeting.json`, uploaded **last**: `schema_version`, `meeting_id` (= the folder name, `^[a-z0-9][a-z0-9-]{2,62}$`), `title`, `language`, `attendees`, and for every file its name, size and SHA-256 (`src/meeting/manifest.py`, Pydantic, `extra="forbid"`). `scripts/upload_meeting.py` builds it with the same model and writes it with `If-None-Match: *` (`--replace` to upload the folder again).
- Why the manifest and not the recording: the trigger sees one blob at a time, so a job started by the recording can't know whether attachments are still on their way; the manifest is the client saying "complete", and its hashes catch a file that is half-written or was swapped. It also keeps big files out of the worker: a Python Blob trigger hands the whole blob to the function (`InputStream`), and the manifest is a few hundred bytes.
- D12 confirmed: `@app.blob_trigger(path="incoming/{meeting_id}/meeting.json", connection="RecordingsStorage", source=func.BlobSource.EVENT_GRID)`. Read in the extension's source (azure-sdk-for-net, `Microsoft.Azure.WebJobs.Extensions.Storage.Blobs`, main on 2026-11-21) to know what the code must handle:
  - `/runtime/webhooks/blobs?functionName=Host.Functions.meeting_job` answers the Event Grid validation handshake, and for a notification takes container, blob name, ETag and blob type from the event's `data`, puts a message on the host's blob-trigger queue and answers 202. The function runs from that queue.
  - It runs on the blob **as it is when the message is processed**. For the Event Grid source it compares no ETag and keeps no blob receipts (both are the polling trigger's), so every duplicate event runs the function again.
  - The `path` pattern is not a filter in this mode: an event for any blob in the account runs the function, just without the pattern's binding data. The filter is the Event Grid subscription's (`subjectBeginsWith` `/blobServices/default/containers/incoming/blobs/`, `subjectEndsWith` `/meeting.json`), and the job checks the path again (`meeting_id_from_path`).
- Locally `scripts/eventgrid_stub.py` plays the system topic: it lists the watched containers every second (Azurite has no change feed), turns a new or changed ETag into a `Microsoft.Storage.BlobCreated` event in the Event Grid schema, applies the same subscription filters, does the validation handshake, and retries/dead-letters like Event Grid (2/4/8/16 s, 5 attempts, 400/413 at once). `POST /_stub/replay` sends an event again with the same id, which is what an Event Grid duplicate is.

## D16 — Limits and checks before any model runs
- In this order, cheapest first, all before Whisper or the LLM: the manifest at most 64 KB and valid (D15); for every file the declared size within its limit (recording 300 MB, attachment 20 MB), the blob present, the stored size equal to the declared one, the **type from the first bytes** (recording: WAV, MP3, MP4/M4A, Ogg, FLAC, WebM; attachment: PDF, or ZIP named `.docx`), then the SHA-256 while streaming (the recording to a temporary file, which speech to text then uses), then the recording's duration from its container with PyAV (at most 60 minutes).
- 60 minutes because D4 refuses transcripts over 40,000 characters (about an hour of speech) before the model call: a longer recording would be refused only after an hour of speech to text. Both limits move together when M3 splits long meetings. All limits are settings (`MAX_RECORDING_MB`, `MAX_ATTACHMENT_MB`, `MAX_RECORDING_MINUTES`, `MAX_MANIFEST_KB`).
- A failed check is permanent (`error.retryable = false`) with a stable code: `invalid_manifest`, `too_large`, `missing_file`, `size_mismatch`, `unsupported_type`, `hash_mismatch`, `unreadable_audio`, `too_long`; later, `no_speech`, `transcript_too_long`, `summary_invalid`. Messages name files and limits, never content (the upload is untrusted, as the transcript is in D4).

## D17 — Stores: one job record per meeting in Cosmos DB, transcripts as blobs
- Cosmos database `meetings`, container `jobs`, partition key `/id`, `id` = meeting id: every access is a point read or write. The record holds the stage and its times, counters (`attempts`, `deliveries`, `ignored_uploads`, `stt_runs` = completed Whisper runs), the manifest's ETag, the checked file list, the transcript's metadata, the grounded summary (a few KB) and its model metadata, `error`, and `history` (earlier errors of a restarted job).
- The transcript is a blob in `transcripts/<meeting-id>/<first 16 hex of the recording's SHA-256>.<STT_MODEL>.json`: keyed by content and model, so a retry, or a new upload of the same bytes after a failure, reuses it instead of running Whisper again.
- `GET /api/meetings/{meeting_id}` (function key on Azure) returns the record without Cosmos system fields; `scripts/meeting_status.py` follows it.
- Connections: `RecordingsStorage` (a connection string, Azurite) or `RecordingsStorage__blobServiceUri` (Azure: the app's managed identity), the same names the Functions host reads for the trigger; `COSMOS_ENDPOINT` + `COSMOS_KEY`, where an empty key means Entra ID and the emulator's published key is the default only for the emulator's own address. Locally `scripts/init_stores.py` creates the two containers and the Cosmos container; on Azure Terraform creates them (M5), and the app never tries.

## D18 — Stages in Cosmos rather than Durable Functions; deliveries are at least once
- Two stages in one function, with the record as the checkpoint, instead of Durable Functions (supported on Flex with the Azure Storage provider): no task hub, no orchestrator replay rules, and the status endpoint is a point read. Revisit if M6's batch transcription needs a long wait between stages.
- Retries, from the extension's source: the blob-trigger queue retries a failed run **at once** (visibility timeout zero) up to `extensions.blobs.poisonBlobThreshold` (5; the `extensions.queues` settings do not apply to this queue), then moves the message to `webjobs-blobtrigger-poison` on the recordings account. While a run is in progress the message is hidden for 10 minutes, renewed halfway; if the host dies, it reappears when that runs out.
- What a delivery means (`src/meeting/job.py`): same manifest ETag and job `summarised` or failed for good = a duplicate (`deliveries` + 1, nothing redone); same ETag and unfinished = a retry, resumed at the stage the record reached; a new ETag restarts a failed job and is ignored (`ignored_uploads` + 1) by any other, so a finished meeting is never silently replaced. The attempt is counted before the work, so a host that dies also uses one; the attempt that reaches `JOB_MAX_ATTEMPTS` (= the poison threshold, a unit test keeps them equal) records `retries_exhausted` with `retryable: true` instead of raising, and delivering the same manifest again (the stub's replay) starts a new round from the stage reached.
- Concurrency: the first write is insert-only and every later write is a replace with `If-Match` on the record's ETag, so of two deliveries running at once one stops at its next write. The work it did until then can be wasted (two Whisper runs), but there is never a second result. No lease: one that a crashed host can't release would have to expire before that host's retry comes back.
- `extensions.blobs.maxDegreeOfParallelism = 1`: one job per instance, Whisper takes the CPUs. Retries without backoff mean an outage of the model burns the five attempts in seconds; with the transcript stored, the replay costs only the summary.

## D19 — Whisper inside the Function on Azure: measured now, decided in M7
- **Status:** open: decided in M7 with these numbers and M7's own
- The deployment package with speech to text in it (`scripts/package_size.py`, `docs/evidence/m2-package-size.md`): faster-whisper's dependencies (PyAV's FFmpeg libraries, CTranslate2, ONNX Runtime for the voice filter) are most of it, and the Whisper small model is about as big again. The model must be in the package (or an image): Flex Consumption gives the host 30 seconds to start, too short to download it.
- Flex Consumption instances: 2,048 MB with about 1 core, or 4,096 MB with about 2; default timeout 30 minutes, no maximum. A one-hour meeting at this laptop's real-time factor with 1–2 cores is in that range but not by much.
- Locally the number of Whisper threads is measured (`scripts/stt_threads.py`, `docs/evidence/m2-stt-threads.md`) and the fastest is the value in `src/local.settings.json.example`.
- Options for M7: Speech batch transcription only (D3); Whisper in the package; Flex Consumption's container-image deployment (preview). M7 measures the Function's real start and transcription time against batch transcription.

## D20 — Lab limits: Ollama capped at 6 CPUs, Whisper at 4 threads (updates D8, D19)
- M2's first real run made the laptop unusable (i7-9750H, 6 cores / 12 threads, WSL 12 GB): Whisper, phi4-mini and the Cosmos emulator together took every CPU, the status endpoint stopped answering and the laptop had to be restarted.
- `docker-compose.yml`: Ollama gets `cpus: "6"`, half the laptop's threads. Measured after the cap: phi4-mini 10.7 tokens/s on its own, the M01 summary 52.0 s (M1: 49.9 s without a cap), so the cap costs the summary nothing and keeps the host and Windows responsive.
- `STT_THREADS=4` (`src/local.settings.json.example`), from `docs/evidence/m2-stt-threads.md`: M01's 84.2 s in 12.9 s with 4 threads, 18.4 s with 2, 28.7 s with 8. More threads than physical cores (hyper-threads) more than doubles the time; M1's 29.8 s at 8 threads was this effect. The Function on Azure (D19) sets the value for its instance size in M7.

## D21 — A model error waits before the host's retry (updates D18)
- M2 run A: five attempts in a row ended in `APITimeoutError` (300 s each). Ollama serves one request at a time (`OLLAMA_NUM_PARALLEL=1`) and keeps generating a request its client gave up on, and the host retries a failed run at once (D18), so every retry queued behind the abandoned generation and timed out too. Alone, the same summary took 64.9 s.
- `JobRunner` now waits before re-raising a model error (`openai.APIConnectionError` incl. timeouts, `RateLimitError`, `InternalServerError`): 30, 60, 120, 120 s after attempts 1–4 (`MODEL_RETRY_BASE_SECONDS`, `MODEL_RETRY_MAX_SECONDS`); the last attempt records `retries_exhausted` without waiting. Other transient errors (stores) still retry at once.
- Why in the function, not the host: the Event Grid blob trigger's queue has no retry delay to configure (D18). The wait keeps the message's lease renewed and stays well inside the 30-minute function timeout (300 s call + 120 s wait). On Flex Consumption the wait is billed execution time; a 429 from Azure OpenAI is the case it will mostly serve there.
- D18's two open points, measured on 2026-11-22: the Cosmos vNext emulator honours `If-Match` (4 integration tests, including the stale-ETag replace that must fail), and a host killed with `kill -9` got its retry back 646 s after the job was received, i.e. the 10-minute lease plus the time the host was down (run I).

## D22 — Attachments: DOCX through Docling, PDF through its text layer (updates D16)
- `src/meeting/documents.py` turns each attachment into numbered text blocks. **DOCX**: Docling 2.151.1 (`docling-slim[format-docx]`, its simple pipeline, no models) to Markdown, cut into blocks at blank lines (at most 1,200 characters, longer ones at line ends), refs `agenda.docx #3`. **PDF**: the text layer, page by page, with pypdfium2 5.15 (PDFium, Apache-2.0 / BSD-3), refs `budget.pdf p2.1` (page 2, block 1).
- Why not Docling for PDF: its PDF pipeline runs a layout model, on PyTorch (`docling-slim[models-local]`: torch, torchvision, docling-ibm-models, weights from Hugging Face) or on ONNX Runtime (`models-onnxruntime`, which on Linux pulls `onnxruntime-gpu`, the same Python module as the `onnxruntime` faster-whisper's voice filter needs). For agendas, briefs and exported slides the text layer is what the summary needs, and the Function stays small: the `docs` group adds 104 MB unpacked and 34 MB zipped to the deployment package (`docs/evidence/m3-package-size.md`: 605 MB / 183 MB with speech to text, against M2's 501 / 149).
- A PDF without a text layer (a scan) is kept with no blocks and a warning; reading it is OCR, which belongs to Document Intelligence on Azure (not decided; behind the same `DocumentReader` interface).
- Checks before reading, after D16's (type from the bytes, size, SHA-256): a DOCX must be a ZIP holding `[Content_Types].xml` and `word/document.xml`, at most 2,000 members, none encrypted, at most 50 MB unpacked (no ZIP bomb); a PDF at most `MAX_ATTACHMENT_PAGES` (50) pages. New code `unreadable_attachment` (damaged, encrypted, not parseable); a ZIP that is not a Word document is `unsupported_type`, too many pages or bytes `too_large`. All permanent, all before Whisper runs.
- Read once, when the job is received: the blocks are stored as `transcripts/<meeting-id>/<first 16 hex of the SHA-256>.<name>.json` (like the transcript, D17) and the file's entry in the record gets `document` (blob, pages, blocks, characters, engine, warnings). A retry reads the blob, not the file.

## D23 — Attachments in the prompt: background with references, never the source of a decision (updates D4, D14)
- Each attachment goes to the model as an `<attachment name="…">` block of `[ref] text` lines, before the `<transcript>` block. Neither block can be opened or closed from inside (both tags are removed from all text), and the system prompt calls both data. An attachment is as untrusted as the transcript: M04's agenda carries an instruction for "the AI assistant".
- With attachments, every item gets a `source`: an `enum` of the block references, or null (D14's pattern), checked again by `ground()`. Without attachments the schema has no `source` at all. `evidence` stays the transcript's times only: what was decided or assigned must have been said; the system prompt says attachments are background.
- `ATTACHMENT_CONTEXT_CHARS` (4,000) of attachment text per call, whole blocks, taking turns (every attachment's first block before any attachment's second); what is cut is recorded (`summary_meta.attachments_cut`). The same text goes with every part of a long meeting (D24).

## D24 — Long meetings: summarised in parts cut at pauses, merged without a second summary (updates D4, D16)
- A transcript longer than `PART_MAX_CHARS` (6,000 characters of `[mm:ss] text` lines, about 1,500 tokens: 4–5 minutes of the scripted meetings' dense talk, about 7 of a real meeting) is cut between segments, at the longest pause in the last quarter of each part. Each part is summarised with the strict schema and only its own times as evidence, and told which part of how many it is.
- The parts' items are merged in time order, and an item whose content words overlap an earlier one of the same kind (and owner) by 60 % or more is kept once. Then one more call, `meeting_merge`, gets the parts' overviews, decisions and tasks and the numbered open questions, and returns the title, the overview and the ids of questions a later part answered (an `enum` of `Q1`…`Qn`: it can drop a question, never write an item). Grounding then runs on the merged summary against the whole transcript. Rewriting the items in a second summary was not chosen: a small model drops and reworded items, and the evidence times would have to be checked again against text the model wrote.
- `TRANSCRIPT_MAX_CHARS` becomes 100,000 (the job's limit now, not one call's). `MAX_RECORDING_MINUTES` stays 60: an hour is about 9 minutes of Whisper on the laptop (D20) plus 8–10 part calls of about a minute each, inside the 30-minute function timeout; 90 minutes would not leave room.
- `summary_meta` records `parts` and `calls`; `meeting_status.py` prints `N parts + merge`.

## D25 — Two more grounding checks: `due` in the meeting's words, a decision that repeats an action item (updates D4, D14)
- `due` is kept only when its words occur, in order, in the transcript (case and punctuation ignored): "Wednesday" and "by Wednesday" stay, phi4-mini's "Wednesday Next, the 15th of March (00:27 mentioned as 'Wednesday')" (M1, M2 runs) goes, so does any date the model worked out. The prompt now says to copy the deadline word for word.
- A decision with the same evidence time as an action item and at least half of its content words is removed with a warning: "I will update the release notes" is a task, and phi4-mini listed it as both in every M1/M2 run. The prompt now says a task someone takes on is not a decision. Deterministic and cheap; the evaluation measures what is left (decision/action confusions, D26).

## D44 — The transcriber on Azure: Speech batch transcription, chosen by `SPEECH_ENDPOINT` (updates D3, D17)
- `STT_ENGINE` is `whisper` or `speech`; when it is not set, `SPEECH_ENDPOINT` decides (set: speech). The stack sets the endpoint and not the engine, so a deployed app can't fall back to Whisper, which has no model on Azure (D19); the contract test fails if the stack ever sets `STT_ENGINE`. `load()` refuses settings that can't work (`speech` without an endpoint, unknown values) before any job starts.
- `meeting.speech.SpeechTranscriber` says `remote = True`: the job hands it the recording's plain blob URL (`BlobStore.url`), never a file, and the Speech resource reads the blob with its own identity (D3). On a retry the job hashes the blob again before submitting: Speech must transcribe the bytes the job was received with. Between that check and the service's own read the blob could still change (no blob versioning): a known limit.
- One segment per recognized phrase (best `nBest`, display form with punctuation), offsets in ticks → seconds, sorted by time; phrases that aren't `Success` or are empty are dropped. Channel 0 only, diarization on with `maxSpeakers` = the attendees (2–35, the 2025-10-15 names `diarization.enabled` / `maxSpeakers`, not the older `diarizationEnabled`); speakers become `Guest-<n>`, a label and never a name (D6). Profanity filter off, as Whisper's transcript keeps what was said.
- Batch transcription takes no phrase list, so the attendees' names can't be passed as hints as Whisper's hotwords are (D6 depends on names being spelled right): the transcript carries the warning `attendee names not passed …`, and M7's comparison with Whisper shows what it costs.
- The stored transcript is keyed by `azure-speech` instead of the Whisper model (`Settings.transcript_key`), so neither engine ever reuses the other's transcript. `stt_runs` now counts completed transcriptions of either kind.

## D45 — How the Function waits for a batch job: polled inside the stage, checkpointed on the record (updates D18, D21)
- The job submits once and writes the Speech job's URL to the record (`speech.job`, `speech.submissions`) before it waits: from then on every delivery polls that job, none submits another. It polls every `SPEECH_POLL_SECONDS` (15) for at most `SPEECH_WAIT_SECONDS` (1,200), then raises `TranscriptionPending`, a transient error: the host delivers again at once and that delivery polls the same job. A contract test keeps the wait at least 10 minutes under `functionTimeout` (30), for the summary after it.
- Chosen over a second trigger (a timer, or Speech's own web hooks, which need an endpoint open to its service tag and a validation handshake) and over Durable Functions: D18's stages stay the only state, the status endpoint still reads one record, and a typical meeting (minutes of audio) finishes inside one delivery. The price: a job that waits longer than one delivery uses attempts (5 × 20 minutes = 100 minutes before `retries_exhausted`), and the replay of D18 resumes polling the same job if it still exists.
- Failures: a job `Failed` with an audio code (`InvalidAudioFormat`, `EmptyAudioFile`, `AudioLengthLimitExceeded`, `BadChannelConfiguration`, `InvalidChannelSpecification`) is permanent (`transcription_failed`, no model call); any other failure, or a job that is gone (404: deleted, or past its time to live), clears `speech.job` so the next delivery submits again. 429, 5xx and no connection are `SpeechUnavailable` and wait like a model error (D21); 401/403/400 are transient without a wait (a role still propagating is the expected one in M7). A succeeded job without a transcription file reads the report's `errorKind`.
- After the transcript is stored the job deletes the Speech job (best effort; `timeToLiveHours` 24 removes it anyway). A delivery that loses the record race right after submitting deletes the job it made, so no orphan keeps running.
- The client is plain HTTP on `httpx`, now a direct dependency (it came only through huggingface-hub; openai 3.57 uses httpx2). No Speech SDK: batch transcription is REST only.

## D46 — Microsoft Entra tokens for Azure OpenAI and Speech (updates D5, D41)
- `OPENAI_AUTH=entra` gives the openai client `get_bearer_token_provider(DefaultAzureCredential(), "https://cognitiveservices.azure.com/.default")` as its `api_key`; the SDK calls it before every request, so a refreshed token is the one sent (a unit test checks this through the real SDK). `key` (the laptop's default) sends `OPENAI_API_KEY`. The stack sets `entra` and no key; `AZURE_CLIENT_ID` picks the app's user-assigned identity, as for the stores.
